# 新設計 仕様

## 設計の核

すべての予測と結果を、オッズパーク座標(oddspark:場:日:番号)で紐付ける。内部IDは使わない。

## 現行の根本欠陥

1. レース情報が消えると、購入記録が「どのレースか」を失う(Grok事故で顕在化)
2. 3つのデータベース間で内部IDの同一性が保証されない
3. 全削除API(DELETE /races/)が残っている

## 7テーブル構成の役割

- 0.競輪場マスタ：バンク特性
- 1.レース結果：確定結果
- 2.レース情報：事前情報
- 2b.レースオッズ：全券種オッズ
- 4.想定：全買い目の予測マスタ。投票有無もここで持つ
- 5.検証：想定と結果の突合値
- 3.集計キャッシュ：画面表示用

## 見送りの扱い

見送りは別テーブルを作らない。
4.想定に全買い目を保存し、voted=0 のものが見送り。購入していない買い目はすべて見送りになる。
これで「見送り記録の登録漏れ」が構造的に起きない。

## 実運用との分断

実運用側(実資金投票・証拠金)は現状維持。検証側とは物理的に独立。
収益ページは集計に使っていないため、検証側刷新の影響は受けない。

## 集計キャッシュの更新方式(遅延計算+ハッシュ検証)

1. 画面から集計要求 → 集計キャッシュを(scope, section, params)で引く
2. source_hash が現在の検証のハッシュと一致 → そのまま返す(高速)
3. 不一致 or 未登録 → 検証を集計して集計キャッシュに保存して返す

source_hash は「検証の件数+最終計算時刻」で十分。検証が更新されれば自動で再計算。

## 上位K件シミュレーション

検証に race_rank_by_ev を持たせる。集計時に race_rank_by_ev <= K で絞るだけで済む。都度ソート不要。

## モデルバージョン分離

想定に model_version を持たせる。集計時は WHERE model_version = 'v2.1' で絞る。全モデル混在/単一モデル両対応可能。

## 移行手順

1. バックアップ(3つのデータベースすべて)
2. 新テーブル作成(DDLは「新設計_テーブル定義」参照)
3. 現行テーブルから新テーブルへデータ移行
4. 移行結果の検証(件数・合計値の一致)
5. 新API実装(集計・取得)
6. フロント切替
7. 旧テーブルを読み取り専用化(削除はしない)

## 到達点(受け入れ条件)

1. 全予測・結果がレースIDで紐付き、レース情報が消えても追える
2. 見送りは想定の voted=0 で表現され、別テーブルが存在しない
3. 集計は集計キャッシュから即答。入力変更時のみ再計算
4. モデルバージョンで集計を切り替えられる
5. 全削除APIが存在しない

## 移行中の一時ルール

新テーブルが安定するまで、現行テーブルは読み取り専用として残す。書き込みは新テーブルのみ。
